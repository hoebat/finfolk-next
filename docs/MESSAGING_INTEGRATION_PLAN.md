# Messaging integration plan

## Goal

Implement and verify reusable Instagram and TikTok messaging integrations around
the Clojure-authored finfolkdb protocol: verified webhook ingestion,
account-specific authorization and credentials, provider sending adapters,
pluggable FinFolk/chat handlers, worker recovery, live PostgreSQL and
provider-contract tests, and a concrete rollout/acceptance procedure. Preserve
historical migrations and the running API until an explicit tested cutover;
distinguish implemented/tested code from live provider activation, and document
any unavailable Business Messaging access without claiming live delivery.

## Fresh-rebuild decision

The user requires regeneration from scratch. The target is a clean database built
from the current Clojure definitions, followed by explicit seed and depth/geo/ocean
imports. There is no additive schema upgrade or historical migration replay in
this release path. This decision supersedes the earlier additive-coexistence
proposal. Keep immutable historical migrations only for the serving legacy path
and its regression fixtures until that path is deliberately retired.

The authoritative rebuild and import plan is
[DATABASE_REBUILD.md](DATABASE_REBUILD.md#fresh-rebuild-and-data-import-plan).
Generation remains pure: installing the generated schema and importing data are
explicit operations on an identified clean candidate. The serving database stays
intact until the replacement and its API have passed acceptance.

## Target architecture

| Boundary | Responsibility |
| --- | --- |
| Clojure-authored finfolkdb | Entire native schema, capitalized linked tables, enums, functions, system seed and database import mutations |
| Import pipeline | Validated geo/site/depth/ocean inputs, provenance, immutable source versions, asset registration and a reproducible import report |
| Provider adapters | Raw signatures, normalization, OAuth, entitlement/subscription checks, encrypted credential access and sending |
| FinFolk application policy | Login, current user eligibility, operator access, explicit social links, follower rules and registered commands |
| Worker | HTTP routing, bounded processing/delivery, queue wakeups, scheduled recovery and refresh |

Managed authentication remains an explicitly provisioned provider dependency. Its
user/password/session tables are not generated by finfolkdb or reconstructed from
legacy application rows. An auth-aware candidate branch can retain that managed
schema while the application schemas are rebuilt from their native definitions.
Verify the actual issuer, user directory and candidate endpoint together before
connecting the Worker. The previously attempted `finfolk_messaging` database has
no schema installed and its auth provisioning error remains unresolved; it is
not the only possible candidate-provisioning path.

The generic gateway's application authorization callbacks and trusted handler
registry remain extension points for other systems. Preserve the tested receipt,
lease, completion, outbox and credential contracts while rebuilding deployment.

pipeline or live provider activation.

## Completion order

1. Implement and verify the complete fresh rebuild/import pipeline described in
   DATABASE_REBUILD.md. Run it against a clean local PostgreSQL database twice
   from the same pinned inputs and compare semantic results.
2. Provision the isolated candidate, install the generated release, seed system
   records, import depth/geo/ocean data and validate its release/import manifests.
   Keep provider accounts disabled and separate live network acquisition from
   reproducible imports. Do not fabricate managed-auth tables to bypass guards.
3. Wire the candidate API to native functions and intended managed authentication.
   Verify actual role grants, current user eligibility and subject-isolated chat.
   The historical API's lowercase SQL cannot simply be pointed at the new schema.
4. Complete first-account onboarding: securely obtain and bind the actual
   provider identity. Current OAuth tests start from a known account ID. Preserve
   operator/nonce/expiry/single-use protections and reconnect generation fencing.
5. Run independently gated app-chat and provider pilots. Verify incoming/outgoing
   IDs against durable receipts/outbox/audit; test duplicates, expiry, pause,
   disconnect and recovery. Keep the legacy ingress until deliberate handover.
6. Complete TikTok's separate data-security/privacy review in parallel, using
   truthful company and implemented data-handling information. Confirm regional
   entitlement, scopes, account-holder OAuth and DIRECT_MESSAGE subscription.
   App verification and fixture tests do not prove messaging entitlement.
7. Promote the verified rebuilt candidate through an explicit cutover. Retain the
   prior database/configuration for rollback. Retire obsolete runtime paths only
   after successful handover; preserve immutable historical release fixtures.

## Acceptance invariants

- Regenerate the full application schema from Clojure; replay no schema migrations.
- Keep required seed data separate from explicit reference-data imports.
- Validate assets and preserve source checksums, provenance, licences, CRS, datum,
  units, depth sign, nodata, acquisition status and quality labels.
- Verify raw signatures before parsing and acknowledge only after durable commit.
- Use trusted account routing, scoped identities and authenticated chat subjects.
- Commit claims before HTTP/model calls; commit domain writes and completion
  together, rolling back stale claims.
- Distinguish accepted, rejected and uncertain sends; never blindly resend an
  ambiguous delivery. Encrypt grants and fence reconnect/refresh races.
- Keep executable handlers in trusted code and personal-command rules in the app.
- Keep accounts disabled until explicit activation and use pilot allowlists.
- Preserve the serving API/database until replacement acceptance and cutover.
- Record local/fixture verification separately from real provider delivery.
